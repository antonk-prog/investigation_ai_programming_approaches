# 11. Multi-agent orchestration

[← к оглавлению](../../README.md)

## Суть

Вместо одного универсального агента — несколько специализированных:

- **planner** — исследует и планирует, не меняет код;
- **implementer** — пишет реализацию;
- **tester** — пишет и гоняет тесты;
- **reviewer** — независимо проверяет результат.

Плюсы: специализация, изоляция контекста, независимое ревью, параллелизм. Минусы: координационные издержки, размножение ошибок, сложная отладка.

Правило: начинать с одного агента + субагентов для read-only исследования и ревью. Полную оркестрацию вводить только когда задача действительно параллелится.

## Что понадобится

Ничего. В opencode есть встроенные субагенты `general`, `explore`, `scout` и механизм `Task`.

Примеры кастомных агентов уже лежат в:

```
├── planner.md
```


## Промпт для старта

Вызов оркестратора (Tab → orchestrator):

```text
Координируй реализацию logstat по ТЗ ../../../docs/00-common-task.md.

Порядок:
1. planner: исследуй задачу и составь план. Код не менять.
2. implementer: реализуй по плану.
3. tester: напиши и запусти тесты по критериям приёмки.
4. reviewer: проверь код и результат, не меняя файлы.
5. Если reviewer нашёл проблемы — верни задачу implementer.

Не переходи к следующему шагу без результата предыдущего.
```

Или вручную:

```text
@planner исследуй ТЗ и составь план. Файлы не меняй.
@implementer реализуй план.
@tester напиши тесты на критерии приёмки и запусти их.
@reviewer проверь реализацию и тесты. Файлы не меняй.
```

## Ход работы

1. Запустите planner. Убедитесь, что он не менял файлы.
2. Передайте план implementer.
3. Tester пишет тесты **независимо** от implementer.
4. Reviewer получает чистый контекст и проверяет.
5. Цикл review → fix до чистого ревью.
6. Сборка и проверка:

```bash
cd ~/Projects/Personal/investigation_ai_programming_approaches
./check.sh approaches/11-multi-agent/impl
```

7. Сравните с одиночным агентом по времени, токенам и числу найденных дефектов.

## Что фиксировать

- Время по шагам (plan / implement / test / review).
- Сколько дефектов нашёл reviewer.
- Сколько дефектов он пропустил.
- Сколько раз агенты противоречили друг другу.
- Сколько токенов/времени ушло на координацию.
- Стало ли лучше, чем один агент.

## Критерии успеха

- [ ] Роли разделены и не смешиваются.
- [ ] Planner и reviewer не меняют код.
- [ ] Reviewer нашёл хотя бы одно замечание.
- [ ] 100% acceptance.

## Типичные ошибки

- **Агенты делают одно и то же.** Нет специализации — нет смысла.
- **Общий контекст.** Если все видят всё, изоляция не работает.
- **Нет арбитра.** Агенты спорят, никто не принимает решение.
- **Ошибка размножается.** Planner ошибся — implementer и tester повторяют.
- **Слишком много ролей.** Координация съедает выигрыш.

## Время

90–150 минут.

## Что сравнить с другими подходами

- Накладные расходы на координацию.
- Качество независимого ревью.
- Когда multi-agent реально оправдан.
