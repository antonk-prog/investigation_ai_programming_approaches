# 10. Eval-Driven Development

[← к оглавлению](../../README.md)

## Суть

Нельзя улучшать то, что не измеряешь. Сначала определяются метрики и набор проверок, потом делается реализация, потом измеряется результат. Любое изменение проходит через eval; регрессия блокируется.

Для детерминированной задачи eval — это acceptance-набор. Для LLM-приложений — датасет, рубрики, LLM-as-judge, метрики качества.

## Что понадобится

Обязательный инструмент уже есть:

```
shared/acceptance/check.py
```

Это black-box harness: он запускает бинарник и проверяет stdout/stderr/код возврата. 35 проверок.

Опционально — promptfoo для оценки качества кода/промптов через LLM:

```bash
npx promptfoo@latest init --example getting-started
npx promptfoo@latest eval
npx promptfoo@latest view
```

Promptfoo требует API-ключ и тратит токены. Для базового эксперимента не нужен.

## Промпт для старта

```text
Прочитай ТЗ ../../../docs/00-common-task.md и shared/acceptance/check.py.

Работаем через eval-driven.

1. Составь матрицу проверок: сценарий → вход → ожидаемый код → ожидаемый вывод.
2. Добавь 5 своих краевых случаев, которых нет в чекере.
3. Реализуй logstat.
4. После каждой итерации запускай ./check.sh и записывай pass rate.
5. Если проверка падает — сначала объясни причину, потом исправляй.
6. В конце сделай мутационную проверку: сломай одну функцию и убедись, что eval это ловит.
```

## Ход работы

1. До кода выпишите eval-матрицу. Минимум — 17 сценариев из ТЗ.
2. Добавьте свои краевые случаи:
   - `--from` позже `--to`;
   - `--module` с несуществующим именем;
   - файл с CRLF;
   - строка с пустым сообщением;
   - очень длинная строка.
3. Реализуйте.
4. Гоняйте чекер после каждой итерации:

```bash
cd ~/Projects/Personal/investigation_ai_programming_approaches
./check.sh approaches/10-eval-driven/impl
```

5. Записывайте pass rate по итерациям.
6. **Мутационная проверка:** намеренно сломайте сортировку модулей или экранирование и убедитесь, что чекер падает. Если не падает — добавьте проверку.
7. Сравните две реализации (например, свою и от другого подхода) по pass rate и числу регрессий.

|---|---|---|---|
| 1 | | | |
| 2 | | | |
| ... | | | |

Дополнительно:

- Сколько проверок добавили сверх ТЗ.
- Сколько дефектов поймали.
- Сколько дефектов **не** поймали.
- Помог ли eval не сломать уже работающее.

## Критерии успеха

- [ ] Eval-матрица создана до реализации.
- [ ] 100% проверок проходят.
- [ ] Мутационная проверка ловит хотя бы одну поломку.
- [ ] Есть история pass rate по итерациям.

## Типичные ошибки

- **Оценивать только happy path.** Ошибки — половина контракта.
- **Подгонять реализацию под чекер.** Чекер — не единственное требование.
- **Метрика без цели.** Непонятно, когда «достаточно хорошо».
- **Забыть про регрессии.** Новые проверки должны запускаться всегда.
- **Ложная уверенность.** 100% acceptance не значит «нет багов».
