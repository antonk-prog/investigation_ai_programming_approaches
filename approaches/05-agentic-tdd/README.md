# 05. TDD / Agentic TDD

[← к оглавлению](../../README.md)

## Суть

Тест — это исполняемая спецификация. Цикл:

```
Red → Green → Refactor
```

В agentic-варианте агент сам крутит цикл: пишет падающий тест, убеждается, что он падает по правильной причине, пишет минимальную реализацию, доводит до зелёного, рефакторит.

Ключевая мысль: TDD — это не про тесты, а про **петлю обратной связи**. Без неё агент «верит», что код работает.

## Что понадобится

Можно без зависимостей: маленький test runner на `assert`. Можно GoogleTest.

Вариант с gtest через FetchContent (нужна сеть при первой сборке):

```cmake
include(FetchContent)
FetchContent_Declare(
    googletest
    URL https://github.com/google/googletest/archive/refs/tags/v1.14.0.tar.gz
)
set(gtest_force_shared_crt ON CACHE BOOL "" FORCE)
FetchContent_MakeAvailable(googletest)
enable_testing()
```

Вариант с системным пакетом:

```bash
sudo apt install libgtest-dev
```

Для эксперимента достаточно `assert`: важен цикл, а не фреймворк.

## Промпт для старта

```text
Прочитай ТЗ ../../../docs/00-common-task.md и фикстуры ../../../shared/fixtures/.

Работаем строго по TDD. Не пиши реализацию, пока тест не написан и не упал.

1. Составь список тестов из критериев приёмки (по одному на сценарий).
2. Начни с первого теста. Покажи код теста.
3. Собери и запусти: тест должен упасть. Покажи вывод.
4. Только теперь напиши минимальную реализацию.
5. Запусти тест: должен пройти.
6. Рефактори, не меняя поведения.
7. Переходи к следующему тесту.

После каждых 2–3 тестов запускай весь набор.
```

Если агент нарушает порядок:

```text
Стоп. Ты начал с реализации. Вернись к шагу 2: сначала тест, покажи, что он падает.
```

## Ход работы

1. Выпишите тесты из сценариев приёмки. Не тестируйте внутренности.
2. Первый тест — самый простой (например, `--help`).
3. Убедитесь, что тест падает **по правильной причине**.
4. Минимальная реализация. Не «на будущее».
5. Рефакторинг только при зелёных тестах.
6. После 2–3 тестов — полный прогон.
7. В конце:

```bash
cd ~/Projects/Personal/investigation_ai_programming_approaches
./check.sh approaches/05-agentic-tdd/impl
```

## Что фиксировать

- Число тестов и их связь со сценариями приёмки.
- Сколько тестов упало по «неправильной» причине.
- Сколько раз агент пытался писать реализацию первой.
- Время цикла на один тест.
- Покрытие (если есть).
- Сколько багов поймали тесты до чекера.

## Критерии успеха

- [ ] Ни одна строка реализации не написана до первого падающего теста.
- [ ] Каждый тест падал до реализации.
- [ ] Все тесты проходят.
- [ ] 100% acceptance.
- [ ] Тесты проверяют поведение, а не реализацию.

## Типичные ошибки

- **Тесты после кода.** Это не TDD, а ретроспективное покрытие.
- **Тестировать приватные методы.** Хрупко и бессмысленно.
- **Медленный цикл.** Если сборка 5 минут, TDD не работает.
- **Один гигантский тест.** Непонятно, что сломалось.
- **Подгонка теста под реализацию.** Тест должен выражать требование.

## Время

90–120 минут.

## Что сравнить с другими подходами

- Сколько дефектов поймано **до** acceptance-чекера.
- Насколько легко ревьюить (тесты как документация).
- Цена поддержки тестов.
