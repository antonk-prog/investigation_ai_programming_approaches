# 01. Spec-Driven Development (OpenSpec)

[← к оглавлению](../../README.md)

## Суть

Код производится из спецификации. Сначала фиксируется **что и зачем**, затем **как**, и только потом появляется реализация. Спека живёт в репозитории, версионируется и служит контрактом для приёмки. После завершения изменения delta-спека вливается в основную спецификацию проекта.

Ключевая идея: ревьюить дешевле спеку, чем дифф. Ошибка в требовании, найденная до кода, стоит минуты; после — часы.

## Что понадобится

OpenSpec CLI уже установлен (1.13.1). В окружении также подключён плагин `@devcxl/opencode-spec` с командами `/opsx-*`.

Проверка:

```bash
openspec --version
```

## Настройка

```bash
cd ~/Projects/Personal/investigation_ai_programming_approaches
impl=approaches/01-spec-driven/impl
cp shared/starter/CMakeLists.txt "$impl/"
mkdir -p "$impl/src"
cp shared/starter/src/main.cpp "$impl/src/"
cd "$impl"
openspec init --tools opencode
```

Если `openspec init` создаёт команды, конфликтующие с глобальным плагином, используйте **только один** способ:

- **A:** глобальные команды `/opsx-propose`, `/opsx-apply`, `/opsx-archive`;
- **B:** CLI `openspec` + сгенерированные проектные команды.

Не смешивайте A и B в одном эксперименте.

## Промпт для старта

```text
Прочитай ТЗ: ../../../docs/00-common-task.md и фикстуры в ../../../shared/fixtures/.

Создай изменение OpenSpec для утилиты logstat.
Сначала proposal: зачем, что меняется, impact, non-goals.
Затем delta-спеку с требованиями и сценариями (WHEN/THEN).
Затем design: решения, альтернативы, риски.
Затем tasks: упорядоченные, проверяемые шаги.

Код пока не пиши. Покажи артефакты на ревью.
```

После ревью:

```text
Примени изменение. Иди по tasks по порядку, отмечай выполненные пункты.
После каждого блока собирай проект и запускай acceptance-чекер.
```

## Ход работы

1. Создайте proposal. Проверьте, что non-goals действительно ограничивают объём.
2. Проверьте спеку: сценарии должны описывать **наблюдаемое поведение**, а не классы и функции.
3. Проверьте design: есть ли альтернативы и риски, или это пересказ кода.
4. Утвердите tasks. Каждая задача должна быть проверяемой.
5. Реализация: агент идёт по tasks, вы — принимаете результат.
6. Сборка и приёмка:

```bash
cd ~/Projects/Personal/investigation_ai_programming_approaches
./check.sh approaches/01-spec-driven/impl
```

7. Архивация:

```text
/opsx-archive logstat-csv
```

или

```bash
openspec archive logstat-csv
```

8. Посмотрите, что осталось в `openspec/specs/` — это и есть накопленная документация.

## Что фиксировать

- Время на proposal / specs / design / tasks / код отдельно.
- Сколько раз меняли спеку после начала кода.
- Сколько требований оказались лишними или недостающими.
- Помог ли design принять решения, или всё было очевидно.
- Сколько задач пришлось переписать.
- Прочитал бы это кто-то кроме вас.

## Критерии успеха

- [ ] Все артефакты созданы до первой строки кода.
- [ ] Спека содержит сценарии, а не реализацию.
- [ ] 100% acceptance.
- [ ] Изменение заархивировано, основная спека обновилась.

## Типичные ошибки

- **Спека = дизайн.** В спеке появляются имена классов и алгоритмы. Это делает её хрупкой.
- **Гигантские tasks.** «Реализовать всё» — не задача. Дробите до проверяемых шагов.
- **Пропущенный design.** Без него агент выбирает решения молча.
- **Спека ради галочки.** Если её никто не читает, она не работает.
- **Смешивание инструментов.** Два набора команд создают два источника истины.
