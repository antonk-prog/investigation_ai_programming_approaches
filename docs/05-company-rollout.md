# Как перенести результаты в Инкомсистем

Заполняйте этот файл после прохождения волн. Ниже — рамка, которую нужно подтвердить или опровергнуть экспериментом.

---

## Принципы внедрения

1. **Сначала контекст, потом методологии.** `AGENTS.md`, ADR и Common Ground дают больше, чем любой тяжёлый фреймворк.
2. **Одна практика — один владелец.** Не дублируйте факты в `AGENTS.md`, спеке и memory bank.
3. **Пилот на реальной задаче.** Не на «hello world»: нужна интеграционная задача среднего размера.
4. **Метрики до и после.** Иначе внедрение превращается в веру.
5. **Человек в контуре.** Ревью, тесты и сборка — обязательные gate.
6. **Безопасность.** Никаких секретов, прод-доступов и данных ограниченного доступа в промптах.

---

## Волны внедрения

### Волна 0 — гигиена (1 неделя)

- [ ] `AGENTS.md` в ключевых репозиториях: сборка, тесты, стиль, запреты, формат коммитов.
- [ ] Зафиксировать разрешённые модели и инструменты.
- [ ] Правило: агент не коммитит и не пушит без явного разрешения.
- [ ] Проверить, что сборка и тесты воспроизводимы локально.

### Волна 1 — базовый процесс (2 недели)

- [ ] Plan-first как режим по умолчанию для нетривиальных задач.
- [ ] ADR для архитектурных решений.
- [ ] Common Ground перед крупными задачами.
- [ ] Пилот: 2–3 разработчика, 5–10 задач.

### Волна 2 — spec-driven (3–4 недели)

- [ ] OpenSpec на одном проекте.
- [ ] Полный цикл propose → apply → archive на 2–3 фичах.
- [ ] Ревью спек, а не только кода.
- [ ] Замер: время до результата, доля реворка, число дефектов.

### Волна 3 — качество (4–6 недель)

- [ ] TDD на критичной логике.
- [ ] BDD-сценарии для приёмочных требований.
- [ ] Eval-harness для повторяющихся задач.
- [ ] Свои skills/команды для частых операций.

### Волна 4 — масштаб (по необходимости)

- [ ] Multi-agent для параллелизуемых работ.
- [ ] BMAD для крупных greenfield/регулируемых проектов.
- [ ] Внутренняя библиотека промптов и шаблонов.

---

## Роли

| Роль | Ответственность |
|---|---|
| Владелец практики | методология, обучение, метрики |
| Тимлид | качество спек и ревью, gate |
| Разработчик | ежедневное использование, обратная связь |
| Архитектор | ADR, границы решений |
| Безопасность | классификация данных, запреты |

---

## Метрики пилота

| Метрика | Как измерять | Цель |
|---|---|---|
| Время до первого результата | от постановки до рабочего кода | −20% |
| Доля реворка после ревью | правки / общий объём | −30% |
| Покрытие новых изменений тестами | отчёт | +20 п.п. |
| Дефекты в первый месяц | баг-трекер | без роста |
| Время ревью | часы на PR | без роста |
| Удовлетворённость | опрос 1–5 | >= 4 |

---

## Что запрещено

- Секреты, ключи, токены, пароли в промптах и репозитории.
- Прод-доступы для агента.
- Коммит без ревью человеком.
- Использование сгенерированного кода без понимания сопровождающим.
- Vibe coding в продакшене.

---

## Чек-лист перед мержем AI-кода

- [ ] Требование/спека существует и актуальна.
- [ ] Тесты есть и проходят.
- [ ] Сборка без новых предупреждений.
- [ ] Нет секретов и отладочных данных.
- [ ] Обработка ошибок и граничные случаи проверены.
- [ ] Код понятен ревьюеру без объяснений автора.
- [ ] Лицензии и сторонние зависимости проверены.
- [ ] Решение (если архитектурное) зафиксировано в ADR.
